从评测结果到改进方向

本轮没有观察到 B 的功能修复收益，但记录指出了具体的改进方向。我把这些观察对应到具体组件，形成下面的改进假设。它们尚未在实现中验证，也没有证明会带来收益。

同一个低分，可能来自修复能力、运行预算，也可能来自评审本身。先沿记录区分原因，才能把反馈送到合适的位置。图中右侧是待验证的假设，不是已经证明有效的修复。

例如，judge 没有给出结果，首先要改进评审的可用性；它不直接说明 agent 修复得差。原实验的失败与缺测继续保留，后续实验单独记录。这样既能看到当前系统的边界，也能检查工程改进是否真正消除了问题。

让验证状态跟随代码版本

根据这次记录，我会优先验证代码版本与测试记录关联这项改进。每次写入产生新的版本标识，测试结果记录所针对的版本与用例来源。再次修改后，旧结果仍然保留，但不再代表当前版本已经验证。

这样，agent 可以直接看到“当前版本的公开测试尚未运行，自建用例已经通过”。明确的状态信息能够为最终说明提供依据，减少对 prompt 提醒和历史消息记忆的依赖。是否真的减少不实声明，仍要用新的运行记录和同一评分标准检查。

分别修改与验证

先在开发集复现问题，每次只改变一个主要因素。例如保持 prompt 不变，单独比较响应预算；或保持预算不变，增加验证状态管理。运行前固定重试条件、次数和评分规则，重试的耗时与 token 也计入成本。这样才能判断收益来自哪项改动。

HTTPError 的具体原因尚未定位，首先补齐诊断信息。参数或认证错误需要修正请求与配置；只有明确的临时错误才适合重试。Judge 的改进则同时检查可用性与人工标签上的准确性，取得更多合法输出不等于判定更可靠。

开发反馈会逐渐进入 prompt。此时旧最终集也成为开发材料，需要新的一组确认任务。任务集、rubric、代码和模型配置一起版本化，才能知道下一轮分数变动来自哪里。

克制的扩展顺序

我的扩展顺序是先增加任务覆盖和证据质量，再根据实际需要增加运行器能力。需要多文件修复时加入真实仓库 checkout 和差异收集；需要不可信代码时加入隔离环境；确实需要判断补丁质量时，增加独立 rubric、人工样本与校准。每项扩展都应服务一个明确判断。

LLM judge 可重复使用同一套模型客户端和证据接口，但不同判据需要各自的输入投影与标准。目前这些需求还不足以支持引入通用插件系统，我倾向于保留直接、可检查的调用关系。

一次变更的工作闭环

提出可检验的假设 → 冻结比较条件 → 取得完整记录 → 分项评分 → 阅读变化与失败 → 决定保留、修改或继续取证。

这次尝试没有得到“换一个 prompt 就修得更好”的答案，但让我看清了几处值得继续验证的设计。接下来，我希望逐项检验这些假设，让新的改动与新的证据对应起来。代码和记录也留在这里，欢迎复核、指出问题，或在不同任务和模型上继续探索。
