从一条记录开始

我希望一次背包修复留下下面这样的记录。它是字段示意：功能、结束状态和声明分别保存，时间和 token 也各有位置。

{
    "task": "knapsack", "version": "A", "repeat": 0,
    "status": "done",
    "functional_pass": true,
    "passed": true,
    "judge": {"status": "ok", "passed": true}
}

要生成它，只需把前面讨论的职责连起来。下面是流程示意，省略文件和异常处理；后面的实现代码均从真实源码提取。

run = 运行_agent(需求, 公开反馈, prompt, 预算)
功能判定 = 验收(最终源码, 独立用例)

代码先组织一次运行，再由外层循环安排任务和版本。每个函数对应这条数据流中的一项职责。

任务与工作目录

task 给出需求、初始代码、公开反馈与独立验收。runner 为每次尝试创建新目录，把初始代码写成 solution.py，只把需求和公开样例交给 agent。独立验收留在评分侧。

任务字段与文件位置

任务在 tasks.json，包含 id、split、slice、prompt、source、public、target、regression。当前 target 与 regression 是两组互补的行为检查，共同决定功能判定。来源、适配与独立 oracle 见 数据集说明。

evalcourse 中，client 连接模型，agent 运行工具循环，grading 执行验收，judge 评审声明，run 组织执行，report 汇总，rejudge 复用保存的证据。

Agent 产生证据

Agent 的循环只有一个关键关系：模型给出工具调用，执行器把结果返回到消息中，模型再决定下一步。没有工具调用而正常给出最终回复时，这次工作结束；用完轮次则记录预算停止。

模型响应选择动作
→
执行工具操作当前文件
→
返回观察继续或交付

三个工具足以承载本次实验：read 读取源码与公开示例，write 替换候选源码，test 验证当前版本。调用参数与返回结果按顺序写入轨迹。

LLM Judge 评审声明

第二个 grader 使用刚才保存的最终回复与工具记录。它发出一条独立模型请求：system 提供固定 rubric，user 提供待评审证据；返回判定和依据。

{{code:evalcourse/judge.py#judge}}

这段代码检查正常结束与 JSON 类型。格式错误时拒绝判定，避免把缺测变成通过。语义是否可靠，还需要第七章所说的人工校准。

evaluate 把这个函数接到运行记录上：只提取工具证据，排除 A/B 标签与主评分；未正常交付标为 skipped，请求或解析失败标为 error。Judge 的 token 和耗时另外保存。

组合一次尝试

现在把各部分接回开头的流程。trial 创建工作目录、记录 agent 运行、读取最终源码、执行功能验收，最后按配置调用 judge，并保存同一次尝试的全部证据。

主成功口径是 functional_pass and status == "done"。因此代码正确但耗尽轮次，仍保留功能通过，同时记录交付未完成。Agent 的计时在独立验收前结束，judge 单独计时。

批量运行与报告

运行与复核

先复核已有证据，再决定是否重新执行。两条路径不需要混在一起：离线复核检查保存的记录能否支持报告；新的模型运行是在当下条件下重新做一次实验。

python -m unittest discover -s tests -v
python tutorial/build.py --check
python -m examples.verify_experiment

复核入口不调用模型、不执行候选程序。它检查计划排程、任务快照哈希、逐次结果与评分记录，再重算报告中的指标。当前源码或 prompt 与冻结条件不同会单独提示。记录内部一致不等于证明模型响应真实，也不等于重新验证修复正确。

新报告将结束状态单独列出：done 是正常交付流程结束，不保证功能通过；budget 是用完轮次；output_limit 是响应额度耗尽；agent_error 是请求或执行异常。原实验保留旧报告，复核入口可从其结果行补充这些诊断计数。

单题 A/B 的运行入口

README 提供模型配置方式。下方命令在一道开发题上运行 A/B 各一次，结果保存在 report.md 与每次 trace 中，适合检查自己的环境能否完成这条链路。后续若调整 prompt，我会在开发集上每次改变一项要求、另存结果，再用新的确认任务检验收益；单题一次的结果只作为诊断线索。模型生成代码需在受限环境中执行。

# After configuring EVAL_BASE_URL / EVAL_API_KEY / EVAL_MODEL
python -m evalcourse.run --split dev --tasks knapsack --repeats 1 --judge --out runs/first-pair

确认链路可用后，按预定协议执行完整开发集与最终集。输出目录必须是新的，原记录始终保留。

python -m evalcourse.run --split dev --repeats 1 --judge --out runs/dev-check
python -m evalcourse.run --split holdout --repeats 3 --judge --out runs/holdout-check

先确认 manifest 的状态为 complete，再读 report；遇到差异，回到对应的 result、solution 和 trace。EVAL_JUDGE_MODEL 可以另选评审模型，默认与被测模型相同。同名模型也可能随服务更新而变化，新运行不保证复现原来的分数。

执行边界与已有记录的重评

评分子进程不是安全沙箱。当前临时目录、超时与环境变量清理只提供复位和故障控制，仅用于当前受控任务，模型生成代码仍需受限环境；接入陌生代码前需要真正受限的执行环境。

python -m evalcourse.rejudge runs/holdout-check --out runs/claims-check 可复用已有证据调用 judge，不重新运行 agent，也不覆盖原批次。它仍需要模型请求；若看结果后改变 rubric，应标为探索性分析。
