怎样构建一组小而可信的任务，让分数对应真实的修复工作？

从任务要代表的能力出发，检查来源、输入契约和验收依据，再固定开发与最终评测的划分。

任务的来源与覆盖

我希望任务有可追溯的错误起点和参考修复，因此从 QuixBugs 选择八道算法修复题，固定上游提交，保存缺陷代码、参考修复和 MIT 许可。它们包含真实基准中的错误程序，规模足够小，便于完整检查源码、验收依据和运行轨迹。

选择依据是可复现、标准库可运行、输入契约清楚，并覆盖不同失效方式。它们仍是经典算法单文件修复，不包含工业仓库的环境安装、跨文件定位或长程协作。公开题目也可能出现在模型训练中。真实来源提升可追溯性，实际难度仍要由运行结果检验。

从源程序到可执行任务

每道任务先有明确需求和合法输入范围，再准备错误起点、公开反馈和独立验收。原始缺陷程序与参考修复都保留来源，使他人能够核查任务究竟来自哪里、改编了什么。

预期结果用独立方法生成：背包用子集穷举，最长公共子串用短串枚举，排序用标准排序，下一排列用小规模排列枚举。这种提供预期答案的独立方法称为 oracle。参考修复必须与这些预期一致。再放入错误修复检查 grader，例如只取价值最大的一个物品，或者排序时误删重复值。

公开样例帮助 agent 观察反馈，独立验收检查最终产物。两者的预期都必须符合任务契约。检验评测集时，还要主动放入看似合理的错误修复，确认测试能够拒绝它们。

本项目的适配与排除记录

上游程序只追加 solve(value) 接口适配。target 与 regression 当前按固定顺序交错分配，两组共同构成行为验收，并非逐例标注的“修复前必失败 / 必通过”集合。wrap 因参考实现可能不推进循环而被排除。完整过程见 任务集构建记录。

开发集与最终评测集

三道开发题组成开发集（dev），用于调接口、检查预算和修改 prompt；五道最终题组成最终评测集（holdout），用于冻结后的比较。划分约束的是这次实验的开发流程，不保证模型没见过题目。一旦看了最终题结果再修改 prompt，这些题就已经成为开发证据，下次确认收益需要新任务。

运行环境

环境决定 agent 能看到什么、能做什么，以及有多少预算。A/B 应使用相同条件，每次尝试从同一份初始代码重新开始。上一轮留下的修复和反馈不能悄悄变成下一轮的优势。具体复位和执行边界在实现章展开。

任务和环境固定以后，每次运行仍可能走出不同路径。要解释差异，就需要保留足够的执行证据。
