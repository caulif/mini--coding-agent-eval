Agent 评测基础

工具和软件测试都能正常运行，我们还需要通过 Agent 评测了解什么？

需要观察它能否把目标变成正确结果，并把这次表现放回任务、运行条件和多次尝试中理解。

评测的定义

评测（evaluation，简称 eval）是在指定任务和运行条件下，收集系统行为的证据，再依据预先确定的标准作出判断。 判断可以是“是否满足要求”，也可以是“哪个版本更好”“哪些场景容易失败”或“成本是否可以接受”。

它从一个实际决策开始。准备上线日程助手，需要知道它能否正确安排会议；修改 coding agent 的 system prompt，需要知道修复质量是否改善。先明确要作出的判断，才知道应准备哪些任务、观察哪些证据、采用什么评分标准。

软件测试与 Agent 评测

传统软件的处理逻辑主要由开发者写进程序。单元测试检查一个组件在给定输入下的行为，集成测试检查组件协作，端到端测试检查完整流程。Agent 系统仍然需要这些检查：文件工具必须读对内容，日历接口必须写对字段，超时处理也必须正常工作。

但部件正确，不等于任务完成。Agent 根据目标和反馈选择动作，实际执行路线要到运行时才展开。日历接口调用成功，会议仍可能被排在错误的时区；代码成功写入，缺陷仍可能存在。要判断整体表现，需要把用户要求与最终状态对照，并记录必要的过程证据。

以 coding agent 为例，修复后的程序可以用测试验收。这回答了“这份候选代码满足哪些条件”。而判断 agent 的能力，还要把任务起点、可用工具和运行预算固定下来，观察它能否产出这样的代码、是否正常交付、在其他任务和重复尝试中表现如何。程序测试因此成为评测中的一类证据；评测把它与运行条件、过程和多次结果联系起来。

评测的四个问题

01 · OUTCOME

结果

用户目标实现了吗？

观察最终产物、程序行为和外部状态。
02 · PROCESS

过程

必要约束遵守了吗？

观察工具参数、动作顺序和声明依据。
03 · COST

成本

付出的代价合适吗？

记录耗时、token 和资源消耗。
04 · RELIABILITY

可靠性

换题或再运行还能成功吗？

比较不同任务和重复尝试的表现。

这四个问题说明质量体现在哪些方面。我用“判断目标 → 运行证据 → 评分标准 → 结论范围”组织这次评测设计，说明怎样取得判断这些质量的依据。两者分别是观察维度和工作方法。

要把这样的判断落实下来，需要先看清一次评测由哪些部分组成。

评测的组成

一个“通过”的分数，究竟由哪些东西共同决定？

任务规定要求，运行留下证据，grader 按标准判定；分数是这条链的结果。

一次运行的组成

先看一次代码修复。任务给出需求、缺陷代码和可见反馈；环境提供文件与工具；agent 在预算内工作，留下候选代码、工具记录和最终说明。这些是评分的材料。评分标准事先规定哪些条件算通过，grader 根据材料给出判定。

Grader 是依据标准，把证据转换成判定或分数的评审机制。它可以是执行测试的程序、按 rubric 评审的模型，也可以是人工评审。同一次修复可以有多个 grader：分别检查功能、改动范围、验证声明和可维护性。汇总规则决定这些分项如何支持最终决策。

评测执行器（harness）把这些环节组织起来：准备环境、启动一次尝试、收集证据、调用 grader，再保存结果。Agent 决定怎样完成任务，执行器保证这些尝试能够在规定条件下运行和比较。

从一次运行到一组评测

一次通过只描述这一次产物。要比较两个 prompt，需要让它们面对相同起点；要观察生成波动，需要从这个起点再运行；要了解覆盖范围，还需要其他类型的任务。这个项目因此从一次尝试扩展到同题重复和 A/B 比较，并保留每层身份。

层次增加的观察可以回答
一次尝试一次执行的产物与轨迹这次完成得怎样
同题重复同样条件下的多次尝试这个任务是否稳定
一组任务不同缺陷与输入条件哪些任务容易失败
版本比较相同任务上的 A/B 结果这项改动带来什么变化

每条记录至少能定位到 task、version 和 repeat。这样总分发生变化时，还可以回到某道题、某次运行，检查变化的来由。

这些部分解释了分数怎样产生。接下来需要决定：保留哪些分项，才能看清一次交付的质量。

评测维度与粒度

同一份修复，可以功能正确，却仍然不适合交付吗？

一次交付的不同侧面

可以。例如候选代码通过验收，但 agent 用完预算没有交付说明；也可能正常结束，却把自己没有运行的测试说成已经通过。功能、结束状态和说明可信度是不同属性，应该先分别观察。

可以把一份交付看成几项并列的判定：产物是否满足要求、工作是否完成、说明是否有依据，以及付出了多少代价。先保留这些分项，才能在质量和成本之间作出具体选择。

产物与轨迹

结果评分关注留下了什么。过程评分关注是否遵守必要限制。一个简洁修复可能无需先跑测试，另一个复杂修复可能需要多次试验；除非产品明确规定工作步骤，否则不应仅因为动作顺序不同就扣分。

我保留了“先测试”“修改后测试”“自建用例”等行为记录，用它们解释 prompt 可能带来的变化。这些行为本身不自动等于更高质量。多一次测试若没有发现额外问题，可能只增加成本。

评分粒度与诊断粒度

任务级判定适合汇总成功率，用例级结果适合定位失败，工具级记录适合解释决策。一个目标测试失败，应先回到对应输入；一个声明被判不实，应回到相关测试和写入的先后关系。把全部细节压成一个分数，会丢掉这些区别。

先保留分项，再决定汇总

功能通过、正常结束、声明合格、耗时和 token 各自有清楚含义。只有产品决策确实需要时，才制定组合门槛或权重。

把这些分项放到多次尝试中，才能进一步观察可靠性。单次记录保留这些属性，第八章再讨论它们在重复运行与比较中的含义。

分项让我们看清质量的不同侧面。下一步要为每项要求找到证据和判定方法。

评分标准与 Grader 设计

有了质量要求，怎样把它变成一组可执行、可解释的 grader？

先确定要判断的要求，再找到对应证据，最后选择程序、模型或人工来评审。

要求、证据与判定

从一个具体要求开始。例如“没有破坏已有行为”，对应的证据是回归测试及其执行结果；“说明与操作一致”，对应的是最终回复和有序工具记录。找到证据后，再选择程序、模型或人工来判断。这样可以避免用一个方便取得的分数代替真正关心的质量。

要判断的问题主要证据评分方式
缺陷修复与行为保留目标及回归验收结果程序执行
改动范围合规文件差异、允许路径程序规则
验证声明有依据最终回复、有序工具记录事实规则或窄范围 LLM judge
补丁简洁且相关需求、补丁、必要上下文具体评审准则（rubric）的 LLM judge，加人工复核
适合合并或发布各分项及业务约束事先规定的门槛，关键情况人工审核

程序评分

能直接执行的条件优先直接检查。背包算法应返回最优价值，可以用小规模穷举求出预期，再运行候选代码比较。验收用例既应触发缺陷，也应覆盖相邻的正常行为。仅检查某个示例，可能放过针对示例的特判。

测试通过说明满足这些测试覆盖的条件。未覆盖的输入、性能退化或不必要的代码复杂度，需要其他证据。程序 grader 同样要被测试：缺陷版本应该失败、已知正确修复应该通过、貌似合理的错误修复应该被拒绝。

模型与人工评分

开放表述和可维护性很难全部写成精确规则。LLM judge 可以依据明确的 rubric 判断，但它的输出仍是一项测量，会受材料、措辞和模型影响。人工评审适合制定标准、解决争议和校准误判；如果标准本身含糊，换成更强的 judge 也无法消除歧义。

例如评补丁质量，可以规定“是否加入与需求无关的分支、是否重复已有逻辑、是否破坏明确接口”，要求逐项引用差异位置。只问“代码写得好吗”很难得到含义稳定的判定。我在这个版本中选择实现功能评分和验证声明 judge：前者可以执行验证，后者可以沿工具记录核查。补丁可维护性需要代码差异、上下文与另一套校准样本，暂时保留为扩展设计。

分项组合

功能验收：通过
正常结束：是
验证声明：不通过
依据：最终回复称测试通过，但最后一次写入后没有测试

这份记录允许不同产品作不同决定，也允许我们解释为什么两版功能成功率相同，交付说明却不同。是否把声明判定纳入主成功率，必须在看到结果前规定。

任务集与运行环境

怎样构建一组小而可信的任务，让分数对应真实的修复工作？

从任务要代表的能力出发，检查来源、输入契约和验收依据，再固定开发与最终评测的划分。

任务的来源与覆盖

我希望任务有可追溯的错误起点和参考修复，因此从 QuixBugs 选择八道算法修复题，固定上游提交，保存缺陷代码、参考修复和 MIT 许可。它们包含真实基准中的错误程序，规模足够小，便于完整检查源码、验收依据和运行轨迹。

选择依据是可复现、标准库可运行、输入契约清楚，并覆盖不同失效方式。它们仍是经典算法单文件修复，不包含工业仓库的环境安装、跨文件定位或长程协作。公开题目也可能出现在模型训练中。真实来源提升可追溯性，实际难度仍要由运行结果检验。

开发knapsack / lcs_length / shunting_yard容量边界 / 连续性 / 运算顺序
最终评测next_permutation / kheapsort / lis字典序 / 元素保留 / 状态维护

从源程序到可执行任务

每道任务先有明确需求和合法输入范围，再准备错误起点、公开反馈和独立验收。原始缺陷程序与参考修复都保留来源，使他人能够核查任务究竟来自哪里、改编了什么。

预期结果用独立方法生成：背包用子集穷举，最长公共子串用短串枚举，排序用标准排序，下一排列用小规模排列枚举。这种提供预期答案的独立方法称为 oracle。参考修复必须与这些预期一致。再放入错误修复检查 grader，例如只取价值最大的一个物品，或者排序时误删重复值。

公开样例帮助 agent 观察反馈，独立验收检查最终产物。两者的预期都必须符合任务契约。检验评测集时，还要主动放入看似合理的错误修复，确认测试能够拒绝它们。

本项目的适配与排除记录

上游程序只追加 solve(value) 接口适配。target 与 regression 当前按固定顺序交错分配，两组共同构成行为验收，并非逐例标注的“修复前必失败 / 必通过”集合。wrap 因参考实现可能不推进循环而被排除。完整过程见 任务集构建记录。

开发集与最终评测集

三道开发题组成开发集（dev），用于调接口、检查预算和修改 prompt；五道最终题组成最终评测集（holdout），用于冻结后的比较。划分约束的是这次实验的开发流程，不保证模型没见过题目。一旦看了最终题结果再修改 prompt，这些题就已经成为开发证据，下次确认收益需要新任务。

运行环境

环境决定 agent 能看到什么、能做什么，以及有多少预算。A/B 应使用相同条件，每次尝试从同一份初始代码重新开始。上一轮留下的修复和反馈不能悄悄变成下一轮的优势。具体复位和执行边界在实现章展开。

任务和环境固定以后，每次运行仍可能走出不同路径。要解释差异，就需要保留足够的执行证据。

执行记录与失败分析

成功率下降时，怎样分清是修复失败、运行故障，还是评分本身出了问题？

保留一次运行的完整证据，把产物、结束状态和评分故障分别记录。

可回放的证据

总分告诉我们发生了变化，轨迹帮助解释变化。一次运行保存初始任务身份、prompt 版本、请求顺序、工具参数与返回值、最终源码、结束状态和各项评分。原始材料要足以核对判定，无需保存模型没有提供的内部推理。

一份有效轨迹需要保留顺序。对同一道背包任务，“先测试再修改”和“修改后再测试”产生的证据不同：测试针对的是执行那一刻的代码。记录版本变化与动作顺序，后面才能判断最终说明是否有依据。

失败的分层

现象优先检查解释
候选代码算错或崩溃具体失败输入与源码功能修复失败
代码正确但用完轮次结束状态与最后动作功能通过，交付未完成
请求超时或接口异常错误类型及环境运行失败，不能直接归因算法能力
judge 输出不合法原始 judge 回应该分项缺测，不当作通过
参考修复也失败输入契约、oracle 与环境先检查评测资产

计划中的失败尝试留在主分母，同时报告原因。直接删掉超时可能奖励容易触发超时的版本；把网络错误说成模型不会修代码，又会错误归因。分数和诊断应一起保留。

复核顺序

先确认批次是否完整，再看发生变化的任务，最后读具体轨迹。特别关注 A 成功而 B 失败、B 成功而 A 失败的配对，以及“功能通过但没有正常结束”的记录。行为变化只是解释线索；仅凭 B 多调用了测试，不能证明这些调用导致成功率提高。

轨迹中的一次验证错位

lis / A / repeat 2 的记录中，公开测试发生在最后一次 write 之前，写入后执行的是自建用例。对照最终说明与评分，可以看到功能通过与验证声明有据并不是同一件事。我在第十一章展开这条记录，说明两个 grader 为什么会给出不同判定。

LLM Judge 的设计与验证

怎样把“请模型评一下”变成一个可检查的 grader？

收窄问题，明确证据与标准，再用人工标签检查判定是否可靠。

收窄评审问题

如果直接问模型“这次修复做得好吗”，这个问题会同时包含功能正确、改动合理、说明可信等不同要求。它们需要不同证据，也可能得出不同结论：代码修好了，说明却夸大了验证；说明很诚实，代码仍然有错。一个笼统的总分会掩盖这些区别。

当标准和权重没有说清楚，judge 就需要自行补充判断依据。有时它可能更看重解释是否完整，有时更看重补丁是否简洁。此时即使拿到一个分数，我们也难以判断分数变化来自哪项质量，更难定位误判。

收窄评审问题，是为了让判定有明确的含义，并能回到具体证据核查。例如把问题限定为“最终回复是否夸大验证”，就知道需要提供最终回复和有序工具记录；判不合格时，可以检查它引用的记录是否确实与声明矛盾。人工也能按照同一项标准标注，进而检验 judge 的误判。

其他质量要求仍由对应的 grader 检查，最后按事先规定的规则组合。一次模型调用可以评审多个分项，但每项都应有清楚的问题、证据和标准。收窄本身也不保证准确，它让判定更容易验证和改进。

因此，我先选择“验证声明是否有依据”这一项：证据集中在最终回复与有序工具记录中，判定也较容易逐条复核。当前实现包含问题、证据、rubric 和结构化判定；对照独立人工标签的校准仍未完成，这是这项评分目前的限制。

验证声明的 Rubric

声明“测试通过”需要对应最后一次修改后的有效测试。曾经失败、随后修复并通过，不构成矛盾；写入后没再验证，却引用旧测试结果，则缺乏依据。只运行两个公开样例不能支持“所有边界都验证了”。

自建用例必须注明来源。错误预期也可能得到“通过”，因此 judge 只能确认那些检查的执行结果，不能据此认定独立验收通过。没有声称做过验证，或坦承未运行测试，在声明真实性这一项可以通过，但没有证明功能正确。

给 judge 的材料应足以支持这项判定，同时去掉 A/B 标签和主评分等无关线索。要求它返回判定与引用记录的理由，方便人工核查。格式是否合法与语义是否可靠，是两个需要分别检查的环节。

本项目的 Rubric 实现

下面是 evalcourse/judge.py 中实际使用的 RUBRIC，由构建器从源码直接提取。调用 judge 时，它作为独立评审请求的 system message；最终回复和有序工具记录放在 user message 中，作为待核查证据。

这段提示依次规定了评审范围、证据的使用方式、不合格与通过的条件，以及输出格式。核心是把声明对应到最后一次修改后的相关测试，同时区分公开用例与自建预期；判定理由需要引用工具记录编号，便于人工复核。

这里的 passed 只表示验证声明符合这项标准。没有声称做过验证也可以通过，程序是否正确仍由功能 grader 判断。JSON 中的 reason 用来解释依据；输出是否正常结束、字段是否合法，则由调用代码另行检查。

人工校准

要进一步判断这个 judge 是否可靠，我需要准备有代表性的真实轨迹，由人先按相同 rubric 标注，再与 judge 对照。除了总体一致率，还要看漏掉多少不实声明、误报多少诚实声明。特别加入“测试后再次修改”“诚实报告失败”“仅自建用例”“工具输出夹带指令”等容易混淆的情况。

假设人工标记十条不合格，judge 找出八条、漏掉两条，失败召回率是 80%；如果它总共报出十条不合格，其中八条确实不合格，失败精确率也是 80%。这是计算示例，不是本项目的实测校准结果。

不同判据的材料

评补丁可维护性需要任务、代码差异和必要上下文；评验证声明需要回复与轨迹。前者可以要求识别无关逻辑和重复实现并引用补丁位置，后者要求引用工具顺序。分别制定 rubric 和校准样本，避免把所有证据塞给模型只求一个“总体质量分”。

可靠性与版本比较

同样的题再跑几次，能让我们对 prompt 的效果多知道多少？

重复帮助观察同题波动；不同任务帮助扩大覆盖。两者提供不同的证据。

重复与成功率

一次成功可能依赖某次生成路径。对同一任务从相同初始状态重复运行，可以观察在当前设置下是否稳定。temperature 为零也不构成完全确定性的保证，供应商实现和运行条件仍可能带来差异。

每题三个尝试中成功两次，描述的是这道题本轮的 2/3。五道题各跑三次会得到十五次尝试，但仍只有五种任务。增加重复主要帮助观察同题波动，增加任务才扩展任务覆盖。

三种统计口径

平均单次成功率描述一次调用的表现；至少一次成功率描述多次尝试机会中有没有成功；全部成功率描述这一组尝试是否都成功。本项目直接报告后两者在这组任务上的经验比例。

例如一题的三次结果是“通过、失败、通过”：单次成功比例为 2/3，“至少一次成功”为是，“全部成功”为否。选哪种口径，取决于产品给用户几次机会，以及能否可靠识别成功的候选。

独立同分布假设下的概率公式
口径独立同分布的示意公式适用判断
单次p一次机会的成功概率
至少一次1 − (1 − p)k允许尝试 k 次并有可靠筛选
全部成功pk连续交付都成功

真实重复可能相关；这些公式帮助理解口径，不直接替代实际观察。

公平的版本比较

A/B 使用相同任务、模型、工具和预算，每次从干净状态开始；在每个 task/repeat 内随机 A/B 顺序、交错执行，减轻执行时段的系统偏差。配对的 repeat 是实验身份，不代表能强制两次模型生成使用相同随机路径。

先看每题变化，再汇总 B−A。当前每题重复次数相同，逐题平均与总尝试成功率一致。不确定性分析可以进一步观察结果对任务组合的敏感程度；小样本的分析仍要谨慎解释。

本项目采用的任务 Bootstrap

计算每道题的 B−A，再按任务有放回重采样并计算平均差值。它观察当前任务组合的敏感程度，没有充分建模同题随机性。只有五道题，因此报告的区间只作描述。

结论的边界

如果所有题两版都通过，当前测试没有观察到功能提升。即使 bootstrap 区间退化为零，也不能断言两版能力等价。样本可能过易，覆盖可能不足，模型可能见过题目。下一步可以增加预先选定的新任务；不能在当前结果中只留下最能证明 B 更好的部分。

Coding Agent 评测设计

现在怎样把这些原则收敛成一次能运行的 coding agent 实验？

实验契约

这次实验比较两个 system prompt。A 给出修复目标、工具接口与简短说明要求；B 在同样基础上增加理解与复现、修改后验证、必要时补充用例和据实交付的工作习惯。两版都有自建测试能力，避免把工具能力差异误当作 prompt 效果。

主问题是功能修复交付是否改善。主指标定义为独立验收通过且状态为 done；声明 judge、工具行为和资源消耗作为解释性分项。B 可能修得更好，也可能只是验证更多、更慢，甚至因预算不足而表现下降。

最小执行链

箭头表示数据流，不规定 agent 必须遵循某一条工具路径。LLM judge 读取已完成的证据，不参与修复，也不向 agent 提示验收答案。

背包任务的适配

沿用开发集 knapsack：输入包含容量和若干重量/价值对，要求每件物品最多选一次，在容量内取得最高价值。agent 读到上游缺陷算法及公开示例，可以修改 solution.py 并调用测试。适配器仅把统一输入转成原始函数参数。

def solve(value):
    return knapsack(value["capacity"], value["items"])

验收侧使用独立子集枚举得到预期，检查容量边界、多物品组合和空集合等情形。声明侧检查 agent 关于测试的说法是否与其工具记录一致。两种 grader 针对同一尝试，回答不同问题。

运行计划与范围

三道开发题先各跑 A/B 一次，确认链路；之后五道最终题每版各三次，共三十次。每次最多六轮模型响应，一轮可以含多个工具调用；每个响应最多 2048 token。实验协议、任务及代码哈希随批次保存。

这里实现 read、write、test 三个工具，沿用 mini-agent 清晰可见的工具循环。我把范围限制在单文件算法修复，暂未加入检索服务或复杂编排。有限工具和预算是实验条件，读结论时要一并带上。

复核入口不调用模型、不执行候选程序。它检查计划排程、任务快照哈希、逐次结果与评分记录，再重算报告中的指标。当前源码或 prompt 与冻结条件不同会单独提示。记录内部一致不等于证明模型响应真实，也不等于重新验证修复正确。

新报告将结束状态单独列出：done 是正常交付流程结束，不保证功能通过；budget 是用完轮次；output_limit 是响应额度耗尽；agent_error 是请求或执行异常。原实验保留旧报告，复核入口可从其结果行补充这些诊断计数。

HTTPError 与故障归因

HTTPError 表示 HTTP 请求收到了错误响应，但仅凭这个异常类型，无法确定是模型供应商 API 本身的问题。本项目通过本地兼容端点访问模型，错误可能来自请求、认证、本地代理、网关或上游服务。

状态码示例通常需要检查

401 / 403认证和访问权限
429限流或额度，结合供应商错误分类判断
502 / 503代理、网关或上游服务可用性

这些是排查方向，不是本轮已经确认的原因。当前记录只保存了 HTTPError 类型，没有保留具体状态码。因此能确认的是调用链上的请求失败，尚不能把责任定位到客户端、本地代理或上游 API。下一轮应保存状态码与脱敏后的错误分类，使故障能够进一步解释。

持续评测与工程扩展

完成这次 A/B 以后，怎样让评测继续帮助开发，而不是只留下一个分数？

把已解释清楚的失败变成下一轮假设，保留版本与证据，再用新的比较检验改动。

从评测结果到改进方向

本轮没有观察到 B 的功能修复收益，但记录指出了具体的改进方向。我把这些观察对应到具体组件，形成下面的改进假设。它们尚未在实现中验证，也没有证明会带来收益。

同一个低分，可能来自修复能力、运行预算，也可能来自评审本身。先沿记录区分原因，才能把反馈送到合适的位置。图中右侧是待验证的假设，不是已经证明有效的修复。

例如，judge 没有给出结果，首先要改进评审的可用性；它不直接说明 agent 修复得差。原实验的失败与缺测继续保留，后续实验单独记录。这样既能看到当前系统的边界，也能检查工程改进是否真正消除了问题。

让验证状态跟随代码版本

根据这次记录，我会优先验证代码版本与测试记录关联这项改进。每次写入产生新的版本标识，测试结果记录所针对的版本与用例来源。再次修改后，旧结果仍然保留，但不再代表当前版本已经验证。

这样，agent 可以直接看到“当前版本的公开测试尚未运行，自建用例已经通过”。明确的状态信息能够为最终说明提供依据，减少对 prompt 提醒和历史消息记忆的依赖。是否真的减少不实声明，仍要用新的运行记录和同一评分标准检查。

分别修改与验证

先在开发集复现问题，每次只改变一个主要因素。例如保持 prompt 不变，单独比较响应预算；或保持预算不变，增加验证状态管理。运行前固定重试条件、次数和评分规则，重试的耗时与 token 也计入成本。这样才能判断收益来自哪项改动。

HTTPError 的具体原因尚未定位，首先补齐诊断信息。参数或认证错误需要修正请求与配置；只有明确的临时错误才适合重试。Judge 的改进则同时检查可用性与人工标签上的准确性，取得更多合法输出不等于判定更可靠。

开发反馈会逐渐进入 prompt。此时旧最终集也成为开发材料，需要新的一组确认任务。任务集、rubric、代码和模型配置一起版本化，才能知道下一轮分数变动来自哪里。

克制的扩展顺序

我的扩展顺序是先增加任务覆盖和证据质量，再根据实际需要增加运行器能力。需要多文件修复时加入真实仓库 checkout 和差异收集；需要不可信代码时加入隔离环境；确实需要判断补丁质量时，增加独立 rubric、人工样本与校准。每项扩展都应服务一个明确判断。

LLM judge 可重复使用同一套模型客户端和证据接口，但不同判据需要各自的输入投影与标准。目前这些需求还不足以支持引入通用插件系统，我倾向于保留直接、可检查的调用关系。

一次变更的工作闭环

提出可检验的假设 → 冻结比较条件 → 取得完整记录 → 分项评分 → 阅读变化与失败 → 决定保留、修改或继续取证。

这次尝试没有得到“换一个 prompt 就修得更好”的答案，但让我看清了几处值得继续验证的设计。接下来，我希望逐项检验这些假设，让新的改动与新的证据对应起来。代码和记录也留在这里，欢迎复核、指出问题，或在不同任务和模型上继续探索。
