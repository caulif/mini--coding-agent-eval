真实结果 · 五道最终评测题，每版每题三次。交付成功要求功能验收通过且正常结束。

实验条件与完整证据

声明评分的覆盖

{{experiment:judge}}

这里需要区分两种没有取得评分的情况。A 的五次是评审错误（error）：四次 judge 响应被截断，一次请求发生 HTTPError，没有取得合法判定。B 的两次是按规则跳过（skipped）：agent 没有正常交付，不进入最终声明评审。

两者都不能算通过，也不能直接判为“声明不真实”。分别保留 error 和 skipped，才能区分评审失败与不满足评审条件。缺测覆盖不同，且尚无独立人工校准，9/10 与 13/13 不能支持可靠的说明质量排名。

HTTPError 与故障归因

HTTPError 表示 HTTP 请求收到了错误响应，但仅凭这个异常类型，无法确定是模型供应商 API 本身的问题。本项目通过本地兼容端点访问模型，错误可能来自请求、认证、本地代理、网关或上游服务。

状态码示例通常需要检查
400参数、请求格式和接口兼容性
401 / 403认证和访问权限
429限流或额度，结合供应商错误分类判断
502 / 503代理、网关或上游服务可用性

这些是排查方向，不是本轮已经确认的原因。当前记录只保存了 HTTPError 类型，没有保留具体状态码。因此能确认的是调用链上的请求失败，尚不能把责任定位到客户端、本地代理或上游 API。下一轮应保存状态码与脱敏后的错误分类，使故障能够进一步解释。

成本与验证行为

{{experiment:cost}}

耗时包含失败尝试。B 的一次请求异常导致完整 token 用量未知，不能据此比较累计成本。两版都使用了自建测试，各调用 16 次；这一提示主要影响能力的使用方式，未赋予 A 所没有的工具。

结果的解释范围

五道公开算法题提供的是局部证据。当前结果没有测量工业仓库修复、补丁可维护性或大规模性能。任务 bootstrap 的描述区间为 [−26.7, 0] 个百分点，也不能把这么小的样本变成普遍能力结论。

对我而言，本轮最有用的发现是：验收通过、正常结束与说明有据需要分别测量；更具体的工作提示也要与响应预算共同检验。下一轮可以预先设计更广的任务覆盖或单独比较预算，并改进 judge 的响应预算与校准。那是新的实验，不能回填成这轮已证明的结论。

这轮比较留下了结果，也暴露了测量的缺口。最后一章把这些发现转成下一轮开发的起点。
