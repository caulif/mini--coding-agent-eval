Agent Evaluation Foundations

If tools and software tests work correctly, what else do we need to learn from agent evaluation?

Whether the agent can turn a goal into a correct result, and how that performance depends on tasks, operating conditions, and repeated attempts.

The meaning of evaluation

Evaluation collects evidence about a system under specified tasks and conditions, then applies predefined criteria to make a judgment. That judgment might concern requirements, a comparison between versions, recurring failures, or acceptable cost.

It starts with a decision. Shipping a scheduling assistant requires evidence that it can arrange meetings correctly. Changing a coding agent's system prompt raises the question of repair quality. The decision determines which tasks, observations, and criteria are relevant.

Software testing and agent evaluation

In traditional software, developers encode most of the processing logic. Unit tests check components, integration tests check their cooperation, and end-to-end tests check complete workflows. Agent systems still need all of these: file tools must read the right content, calendar APIs must write the right fields, and timeouts must work.

Correct components do not guarantee task completion. An agent chooses actions from a goal and feedback; its path unfolds at runtime. A successful calendar API call can schedule a meeting in the wrong time zone. A successful file write can leave the bug intact. Evaluating the whole system requires comparing the request with the final state and retaining relevant process evidence.

For a coding agent, tests can validate the repaired program. That answers which conditions this candidate satisfies. Evaluating the agent also means fixing the starting point, available tools, and budget, then observing whether it produces such a candidate, completes normally, and performs similarly on other tasks and repeated trials. Program tests become one source of evidence within this broader comparison.

Four evaluation questions

01 · OUTCOME

Outcome

Was the user's goal achieved?

Inspect artifacts, program behavior, and external state.
02 · PROCESS

Process

Were necessary constraints respected?

Inspect tool arguments, action order, and evidence for claims.
03 · COST

Cost

Was the expense acceptable?

Record time, tokens, and resource use.
04 · RELIABILITY

Reliability

Does success persist across tasks or retries?

Compare different tasks and repeated attempts.

These questions describe dimensions of quality. I organize this experiment around “decision → evidence → criteria → scope of conclusions” to explain how to obtain grounds for judging those dimensions. One is a set of things to observe; the other is a way to organize the work.

Making these judgments concrete starts with the parts of a single evaluation.

The Parts of an Evaluation

What determines a passing score?

The task sets requirements, execution produces evidence, and graders apply criteria. The score is the result of that chain.

The parts of one run

A repair task provides a request, buggy code, and visible feedback. The environment provides files and tools. The agent works within a budget, leaving candidate code, tool records, and a final message. These are the grading materials. Criteria define success in advance; graders apply them to the materials.

A grader is a mechanism that turns evidence into a judgment or score using defined criteria. It may be a test program, a model applying a rubric, or a human reviewer. A single repair can have multiple graders for functionality, allowed changes, verification claims, and maintainability. An aggregation rule determines how those findings support a decision.

Dimensions and Granularity

Can a functionally correct repair still be unsuitable for delivery?

Different aspects of a delivery

Yes. The candidate may pass acceptance tests while the agent exhausts its budget without a final response. Or it may finish normally while claiming to have run tests it never ran. Functionality, termination, and trustworthy reporting are separate attributes.

A delivery can be described through parallel judgments: whether the artifact meets requirements, whether the work completed, whether the explanation is supported, and what it cost. Keeping these separate supports concrete quality–cost decisions.

Artifacts and traces

Outcome grading examines what was left behind. Process grading examines necessary constraints. A small repair may not need an initial test run; a complex one may require several experiments. Unless the product requires a particular workflow, different action orders alone are not grounds for a penalty.

I retain observations such as testing before editing, testing after editing, and creating additional cases to help explain possible prompt effects. Those behaviors do not automatically imply higher quality. Another test call that discovers nothing may only add cost.

Grading and diagnostic granularity

Task-level judgments support success-rate summaries. Case-level results locate failures. Tool-level records explain decisions. A failed test points back to an input; an unsupported claim points back to the order of writes and tests. A single combined score loses these distinctions.

Retain components before aggregating

Functional success, normal completion, supported claims, time, and tokens each have a distinct meaning. Combined gates or weights are useful when a product decision actually requires them.

Reliability emerges when these attributes are observed across multiple trials. Section eight examines repetition and comparison.

Separate findings expose different aspects of quality. Each now needs appropriate evidence and a grading method.

Criteria and Grader Design

How can a quality requirement become an executable, interpretable set of graders?

Identify the requirement, find the evidence, then choose programmatic, model, or human assessment.

Requirements, evidence, and judgments

“Preserves existing behavior” calls for regression tests and their results. “The explanation matches the actions” calls for a final response and ordered tool records. Choosing the judge after identifying the evidence helps avoid substituting an easy-to-measure score for the quality that matters.

RequirementMain evidenceGrading approach
Fix the defect and preserve behaviorTarget and regression checksProgram execution
Respect allowed changesFile diff and allowed pathsProgrammatic rules
Support verification claimsFinal response and ordered tool recordsFact checks or a narrowly scoped LLM judge
Keep the patch relevant and maintainableRequest, diff, and necessary contextA specific rubric, LLM assessment, and human review
Accept for merge or releaseFindings plus business constraintsPredefined gates; human review where needed

Programmatic grading

Directly executable conditions are best checked directly. For knapsack, exhaustive search over small inputs can produce expected optimum values for comparison with candidate code. Acceptance cases should trigger the defect and cover nearby behavior; one example can let a special-case patch slip through.

Passing establishes the conditions covered by those tests. Uncovered inputs, performance regressions, and unnecessary complexity require other evidence. The grader itself needs checks: the buggy version should fail, a known correct repair should pass, and plausible wrong repairs should be rejected.

Model and human grading

Open-ended statements and maintainability are difficult to express entirely as exact rules. An LLM judge can apply a clear rubric, but its output remains a measurement affected by the materials, wording, and model. Humans help define criteria, resolve disagreements, and calibrate errors. A stronger judge cannot resolve ambiguity in the criteria themselves.

A patch-quality rubric might ask whether changes introduce irrelevant branches, duplicate existing logic, or break an explicit interface, with references to diff locations. Asking only “Is this good code?” rarely produces a stable judgment. I implement functional grading and a verification-claims judge here: one executes checks, the other can be inspected against a trace. Maintainability needs diffs, context, and separate calibration samples, so it remains an extension.

Combining findings

Functional acceptance: pass
Normal completion: yes
Verification claims: fail
Evidence: the final response says tests passed,
but no test followed the last write

This record supports different product decisions and explains how equal functional success can coexist with different reporting quality. Whether claims affect the primary success metric must be fixed before inspecting results.

Criteria determine how to judge a run. Task selection determines what those judgments can represent.

Tasks and Environments

How can a small task set produce credible evidence about repair work?

Start with the capabilities it should represent, inspect provenance, input contracts, and acceptance criteria, then freeze the development and final-evaluation split.

Task provenance and coverage

I wanted traceable buggy starting points and reference repairs, so I selected eight algorithm-repair tasks from QuixBugs. The upstream commit, buggy programs, reference repairs, and MIT license are preserved. The tasks are small enough to inspect their code, acceptance criteria, and full traces.

Selection favors reproducibility, standard-library execution, explicit input contracts, and different failure modes. These remain single-file algorithm repairs, without industrial repository setup, cross-file diagnosis, or long-running collaboration. Public problems may also occur in model training data. Provenance improves traceability; actual difficulty still needs empirical examination.

SplitTasksConditions of interest
Developmentknapsack / lcs_length / shunting_yardCapacity boundaries / contiguity / operator order
Final evaluationnext_permutation / kheapsort / lisLexicographic order / element preservation / state
Final evaluationmergesort / find_first_in_sortedRecursive termination / search boundaries

From source program to executable task

Each task specifies a request and valid input domain, then supplies a buggy starting point, public feedback, and independent acceptance checks. Original buggy and reference programs retain their provenance so others can inspect the adaptation.

Expected outputs come from independent methods: subset enumeration for knapsack, short-string enumeration for longest common substring, standard sorting, and small permutation enumeration for next permutation. Such a source of expected answers is an oracle. Reference repairs must agree with it. Plausible wrong repairs also test the grader, such as taking only the highest-value item or deleting duplicates during sorting.

Public examples provide feedback to the agent; independent acceptance checks inspect its final artifact. Both must match the task contract. Testing plausible wrong repairs helps establish that the checks can distinguish relevant mistakes.

Adaptations and exclusions

The upstream programs receive only a solve(value) adapter. target and regression are allocated in a fixed alternating order; together they form behavioral acceptance checks. They are not individually labeled as necessarily failing or passing before repair. wrap was excluded because its reference implementation may fail to advance its loop. See the task construction notes.

Development and final evaluation sets

Three development tasks support interface checks, budget checks, and prompt changes. Five holdout tasks support the frozen comparison. This split constrains the experiment's development process; it does not guarantee the model has never seen the problems. Once final results influence prompt changes, those tasks become development evidence and a new confirmation set is needed.

The execution environment

The environment determines access, actions, and budget. A/B uses the same conditions, and every trial restarts from the same source. Earlier repairs or feedback must not become an unnoticed advantage in later attempts. Reset behavior and execution boundaries appear in the implementation section.

Even with fixed tasks and environments, runs may take different paths. Explaining that variation requires execution records.

Traces and Failure Analysis

When success drops, how can we distinguish a bad repair from an execution failure or a grading problem?

Retain the evidence from each run and record artifact quality, termination, and grading failures separately.

Inspectable evidence

A summary shows that something changed; a trace helps explain it. Each run retains task identity, prompt version, request order, tool arguments and results, candidate source, termination, and grades. These materials should support checking the judgment without claiming access to internal reasoning the model did not supply.

Order matters. On the same knapsack task, testing before a write and testing after it establish different evidence: tests apply to the code that existed when they ran. Tracking changes and action order makes final claims inspectable.

Layers of failure

ObservationFirst evidence to inspectInterpretation
Candidate computes incorrectly or crashesFailing input and sourceFunctional repair failure
Correct code but exhausted turnsTermination and last actionFunctional pass, incomplete delivery
Request timeout or API exceptionError type and environmentExecution failure, not direct evidence of algorithmic inability
Invalid judge outputRaw judge responseMissing assessment, not a pass
Reference repair also failsInput contract, oracle, environmentInspect evaluation assets first

Planned failures remain in the primary denominator, with reasons reported. Removing timeouts can favor versions prone to timing out. Calling a network error an algorithmic failure misattributes it. Scores and diagnostics belong together.

Review order

First establish batch completeness, then inspect changed tasks and individual traces. Useful cases include A passing while B fails, the reverse, and functional success without normal completion. Behavior is an explanatory clue: more test calls alone do not show that those calls caused success.

A verification mismatch in a real trace

In lis / A / repeat 2, public tests precede the final write; only agent-authored tests follow it. Comparing the final message and grades shows why functional success and supported verification claims differ. Section eleven examines this record in detail.

Ordered records make open-ended claims checkable. Verification claims provide a concrete case for designing an LLM judge.

LLM Judge Design and Validation

What turns “ask a model to review it” into an inspectable grader?

A narrow question, explicit evidence and criteria, and human labels for checking judgment quality.

Narrowing the assessment

“Was this a good repair?” combines functional correctness, appropriate changes, and trustworthy reporting. Those need different evidence and can yield different answers: code may be fixed while its verification is overstated, or the report may be honest while the code remains wrong. A broad score hides those differences.

Without clear criteria and weights, the judge fills in its own priorities. One response may favor completeness of explanation; another may favor a concise patch. A changing score then becomes difficult to interpret or diagnose.

Narrowing gives the verdict a specific meaning that can be checked against concrete evidence. Asking whether the final message exaggerates verification identifies the required materials: the final response and ordered tool records. A failing verdict can be checked against its cited records. Humans can label the same criterion to examine judge errors.

Other requirements belong to corresponding graders and predefined aggregation rules. One model call can assess several dimensions, provided each has a clear question, evidence, and criteria. Narrow scope does not guarantee accuracy; it makes validation and improvement more tractable.

I therefore start with supported verification claims. The evidence is concentrated in a final response and a tool trace, and individual judgments are relatively easy to inspect. The implementation includes the question, evidence, rubric, and structured verdict. Independent human-label calibration remains incomplete.

The verification-claims rubric

A claim that tests passed needs relevant test evidence after the last modification. An earlier failure followed by a verified fix is not a contradiction. Citing old tests after a new write lacks support. Two public examples cannot establish that every edge case was checked.

Agent-authored cases retain their source label. Incorrect expectations can also produce a “pass,” so the judge can confirm that those checks ran, not that independent acceptance succeeded. Making no verification claim, or honestly reporting that tests were not run, can pass this narrow criterion without establishing functional correctness.

The judge receives enough evidence for that criterion, without A/B labels or the primary grade. It returns a verdict and references to supporting records. Output format and semantic reliability are separate checks.

The rubric used in this project

The following RUBRIC is extracted directly from evalcourse/judge.py. It is the system message of an independent review request; the final response and ordered tool records are evidence in the user message.

The prompt defines scope, evidence handling, failure and pass conditions, and output format. It ties claims to relevant tests after the last edit, distinguishes public cases from agent-authored expectations, and requests tool-record numbers for human inspection.

passed means only that verification claims satisfy this rubric. No claim can pass; functional correctness still belongs to the program grader. reason records the basis, while the caller checks normal termination and field validity.

Human calibration

To assess reliability, I need representative real traces labeled by people using the same rubric, then compared with judge predictions. Agreement alone is insufficient: the review should count unsupported claims missed and honest claims falsely flagged. Useful cases include another edit after tests, honest failure reports, agent-authored tests only, and instructions embedded in tool output.

If humans label ten failures and the judge finds eight, failure recall is 80%. If eight of its ten failure predictions are correct, failure precision is also 80%. This is an arithmetic example, not a measured calibration result for this project.

Evidence for different criteria

Maintainability requires the request, diff, and relevant code context; verification claims require the final message and trace. The former can ask for irrelevant or duplicated logic with patch references; the latter cites tool order. Each needs its own rubric and calibration samples rather than an undifferentiated “overall quality” score.

Once a single verdict has a clear meaning, repeated attempts can reveal stability and differences between versions.

Reliability and Version Comparison

What can repeated runs of the same task tell us about a prompt's effect?

Repeats reveal variation within a task; different tasks expand coverage. They provide different evidence.

Repetition and success

A successful attempt may depend on one generated path. Repeating a task from the same starting state reveals stability under the current settings. Temperature zero does not guarantee determinism; provider implementation and operating conditions can still vary.

Two successes in three attempts describe this task's observed 2/3. Five tasks repeated three times produce fifteen attempts, but still only five tasks. Repetition mainly examines within-task variation; additional tasks extend coverage.

Three success measures

Per-attempt success describes performance in one opportunity. Any-success asks whether at least one attempt succeeded. All-success asks whether every attempt in the group succeeded. This project reports the latter two as empirical proportions of tasks.

For a task with pass, fail, pass, the observed per-attempt rate is 2/3, any-success is true, and all-success is false. The useful measure depends on how many opportunities the product provides and whether it can reliably identify a successful candidate.

Probability formulas under independent, identical trials
MeasureIllustrative formulaRelevant setting
Single attemptpOne opportunity
At least one success1 − (1 − p)kk attempts with reliable selection
All attempts succeedpkEvery delivery must succeed

Real attempts may be correlated. These formulas explain the measures; they do not replace observation.

Fair version comparisons

A/B uses the same tasks, model, tools, and budget, starting fresh every time. Within each task/repeat pair, randomized A/B order interleaves execution to reduce systematic time effects. The repeat identifier pairs experimental records; it does not force identical model randomness.

Per-task changes precede the aggregate B−A. Equal repeat counts here make task-averaged and trial-averaged success rates agree. Uncertainty analysis can explore sensitivity to task composition, but small samples still require cautious interpretation.

The task bootstrap used here

Compute B−A for each task, resample tasks with replacement, and average their differences. This explores sensitivity to the observed task mix without fully modeling within-task stochasticity. With only five tasks, the interval is descriptive.

Limits of the conclusion

If both versions pass every task, this test has not observed a functional gain. Even a bootstrap interval collapsing to zero cannot establish equivalent capabilities. Tasks may be easy, coverage narrow, or problems familiar from training. A next experiment can add tasks selected in advance; it cannot selectively retain only results favoring B.

Tasks, repetitions, and comparison conditions determine the scope of the conclusion. The next section records the choices I fixed for this experiment.

Coding Agent Experiment Design

How do these principles become a runnable coding-agent experiment?

Freeze the choices as an experimental contract, then run A and B through the same execution chain.

The experimental contract

This experiment compares two system prompts. A gives the repair goal, tool interface, and a short factual reporting requirement. B adds working habits: understand and reproduce, verify after editing, add cases when useful, and describe only verified work. Both versions can create test cases, keeping tool capability separate from prompt effects.

The main question is whether successful repair delivery improves. The primary metric requires independent functional acceptance and normal completion. The claims judge, tool behavior, and resource use are explanatory components. B might repair better, merely test more and run slower, or perform worse when its budget runs out.

The minimal execution chain

Arrows describe data flow, not a required tool sequence. The LLM judge reads completed evidence; it neither repairs the program nor supplies acceptance answers to the agent.

Adapting the knapsack task

The development task supplies a capacity and weight/value pairs. Each item may be selected once; the goal is maximum value within capacity. The agent receives the upstream buggy algorithm and public examples, can modify solution.py, and can run tests. An adapter maps the common input to the original function arguments.

def solve(value):
    return knapsack(value["capacity"], value["items"])

Acceptance uses independent subset enumeration for capacity boundaries, combinations, and empty sets. The claims grader compares statements about testing with tool records. Two graders examine the same attempt and answer different questions.

Run plan and scope

Each of three development tasks gets one A/B pair to check the execution chain. Each of five final tasks then gets three attempts per version, totaling thirty. Each attempt permits six model responses; a response may contain multiple tool calls and has a 2048-token maximum. The batch retains the protocol and task/code hashes.

The implementation uses read, write, and test, following mini-agent's explicit tool loop. I limit scope to single-file algorithm repairs, without retrieval services or elaborate orchestration. Those tools and budgets are part of the experimental conditions and therefore part of the conclusion.

With the contract fixed, the code needs to prepare, execute, grade, and record each attempt.

How do these choices connect into a complete run in code?

The implementation centers on one record: the agent produces code and a trace, graders add findings, and the harness saves and aggregates them.

Starting from a record

I want a knapsack attempt to leave a record like this. This is a field illustration: functionality, termination, and claims remain separate; time and tokens have their own fields in the full record.

Producing it connects the responsibilities already described. This flow sketch omits file and exception handling; implementation blocks below come directly from source.

restore_initial_source(task)

The code organizes one attempt first, with an outer loop scheduling tasks and versions. Each function owns one responsibility in that data flow.

Tasks and workspaces

A task supplies the request, initial source, public feedback, and independent checks. The runner creates a fresh directory, writes solution.py, and exposes only the request and public examples to the agent. Independent acceptance stays on the grading side.

Task fields and source locations

tasks.json contains id, split, slice, prompt, source, public, target, and regression. target and regression are complementary behavioral checks that jointly determine functional success. Provenance, adaptation, and independent oracles are described in the dataset notes.

Within evalcourse, client connects to the model, agent runs the tool loop, grading executes acceptance checks, judge assesses claims, run orchestrates trials, report aggregates results, and rejudge reuses recorded evidence.

The agent produces evidence

The loop has one central relationship: the model requests tools, the executor returns their results in messages, and the model decides what to do next. A normal final response without tool calls ends the attempt; exhausting turns records a budget stop.

Three tools support this experiment: read returns source and public examples, write replaces the candidate, and test checks the current version. Arguments and results are recorded in order.

test() runs public cases by default; test(cases=...) accepts one to eight agent-authored cases. Feedback retains its source because authored expectations can be wrong. They support repair, not independent acceptance.

The program grader checks the artifact

After the agent stops, the runner reads the source actually left behind and executes independent cases. The outer judgment is short: both groups must pass.

check takes candidate source and cases, returning a verdict and individual results. It runs in a fresh directory and separate subprocess, distinguishing valid grading, candidate errors, and timeouts.

Runnable example · checking the grader

The LLM judge assesses claims

The second grader uses the saved final response and tool records. It makes an independent model request: a system message supplies the rubric, a user message supplies evidence, and the response contains a verdict and rationale.

The code checks normal termination and JSON types. Invalid output is rejected instead of converting missing data to a pass. Semantic reliability still requires the human calibration discussed in section seven.

evaluate connects the judge to a run: it projects tool evidence, excludes A/B labels and primary grades, marks incomplete deliveries skipped, and records request or parsing failures as error. Judge tokens and time are separate.

Implementation · judge integration and recording
Connecting an existing mini-agent

The message adapter aligns calls and results by tool_call_id, determines completion from a real end event, and invokes the same judge. It assumes sequential tool records and introduces no mini-agent runtime dependency.

Assembling one attempt

trial connects the pieces: create a workspace, record agent execution, read final source, run functional checks, optionally assess claims, and save the evidence for the same attempt.

Primary success is functional_pass and status == "done". Correct code with exhausted turns retains its functional pass while recording incomplete delivery. Agent timing ends before independent acceptance; judge timing is separate.

Implementation · trial

Batch execution and reports

The batch entry point assigns task/version/repeat identities and ordering, then calls trial repeatedly. Each result is immediately written to JSONL. The manifest freezes tasks, prompts, budgets, and source hashes for inspection.

Aggregation checks complete A/B pairing before calculating success rates, per-task differences, and judge findings. It reads existing records without rerunning the agent.

Implementation · pairing and statistics

Running and inspecting

Offline inspection checks whether saved records support the report. A new model run conducts another experiment under current conditions. They are different operations.

python -m unittest discover -s tests -v
python tutorial/build.py --check
python -m examples.verify_experiment

The audit calls no model and executes no candidate. It checks the schedule, task snapshot hash, per-trial results, and grade evidence, then recomputes metrics. Differences between current code/prompts and frozen conditions are reported. Internal consistency does not authenticate historical model responses or revalidate repairs.

New reports list termination states separately: done means normal completion, not guaranteed functional correctness; budget means exhausted turns; output_limit means exhausted response tokens; agent_error means a request or execution exception. Original reports remain unchanged; the audit derives these additional counts from their rows.

A single-task A/B entry point

The README explains model configuration. This command runs A/B once each on one development task, saving report.md and traces to check the execution chain in another environment. For later prompt changes, I would vary one requirement at a time on development tasks, save new results, and confirm gains on new tasks. One task and one repeat provide only diagnostic evidence. Model-generated code requires a restricted environment.

# After configuring EVAL_BASE_URL / EVAL_API_KEY / EVAL_MODEL
python -m evalcourse.run --split dev --tasks knapsack --repeats 1 --judge --out runs/first-pair

Once the chain works, the predefined protocol covers full development and final batches. Each output directory must be new; earlier records remain intact.

python -m evalcourse.run --split dev --repeats 1 --judge --out runs/dev-check
python -m evalcourse.run --split holdout --repeats 3 --judge --out runs/holdout-check

A complete manifest precedes report interpretation. Differences lead back to result, solution, and trace files. EVAL_JUDGE_MODEL can select another judge model; by default it uses the agent model. A model name may outlive a service-side update, so new runs need not reproduce old scores.

Execution boundaries and rejudging saved evidence

Grading subprocesses are not a security sandbox. Temporary directories, timeouts, and environment cleanup provide reset and fault control for these controlled tasks. Model-generated code still needs a restricted environment.

python -m evalcourse.rejudge runs/holdout-check --out runs/claims-check reuses saved evidence without rerunning the agent or overwriting the source batch. It still makes model requests. A rubric changed after inspecting results makes the new assessment exploratory.

The implementation now connects to saved evidence. The real experiment shows what that evidence can say about the original question.

HTTPError and attribution

HTTPError means an HTTP request received an error response. The exception type alone does not identify the model provider's API as the cause. This experiment accessed the model through a local compatible endpoint; the request, authentication, local proxy, gateway, or upstream service could be involved.

Scope of interpretation

Five public algorithm tasks provide local evidence. This experiment does not measure industrial repository repair, patch maintainability, or large-scale performance. The descriptive task-bootstrap interval of [−26.7, 0] percentage points cannot turn this small sample into a general capability conclusion.

For me, the most useful finding is that functional acceptance, normal completion, and supported reporting need separate measurements. More explicit working instructions also need evaluation together with response budgets. Broader task coverage, a controlled budget comparison, and judge budgeting and calibration are possible next experiments, not already established gains.

Continuous Evaluation and Engineering

How can evaluation keep informing development after this A/B comparison?

Turn explained failures into hypotheses, preserve versions and evidence, and test changes in new comparisons.

From observations to design changes

This batch showed no functional benefit for B, but identified concrete directions. I map the observations to components and formulate improvement hypotheses below. These changes have not been validated in the implementation and are not established gains.

A low score may reflect repair ability, execution budgets, or grading itself. Following the record helps direct feedback to the appropriate component. The right-hand column contains proposed checks, not proven fixes.

For example, a judge that returns no verdict first calls for better assessment availability; it does not directly mean the agent repaired badly. Original failures and missing results remain, with follow-up experiments recorded separately. This exposes current limits and makes improvement testable.

Verification state tied to code versions

Based on these records, I would prioritize testing code-version-aware verification. Each write creates a version identifier; each test records its version and case source. After another edit, old results remain available but no longer imply that the current code is verified.

The agent could then see “public tests have not run on this version; authored cases have passed.” Explicit state can support its final message and reduce reliance on prompt reminders and historical-message recall. Whether it reduces unsupported claims still needs new runs under the same criteria.

Separate changes and validation

Reproduce a problem on development tasks and change one main factor at a time: hold the prompt fixed while comparing budgets, or hold budgets fixed while adding verification-state tracking. Retry conditions, limits, and scoring should be fixed before execution, with retry time and tokens counted. This makes attribution more credible.

The HTTPError cause remains unlocalized, so diagnostic evidence comes first. Parameter or authentication errors require request/configuration fixes; only clearly temporary failures suit retries. Judge improvements need checks of both availability and accuracy against human labels. More valid outputs do not by themselves establish more reliable judgments.

Development feedback will influence prompts. The old final set then becomes development material, requiring new confirmation tasks. Versioning tasks, rubrics, code, and model settings together makes later score changes interpretable.

A restrained expansion plan

I would expand task coverage and evidence quality first, then add runner capabilities when needed. Multi-file repair calls for real repository checkouts and diff collection. Untrusted code calls for isolation. Patch-quality assessment calls for a separate rubric, human samples, and calibration. Each addition should serve a specific decision.

LLM judges can reuse the client and evidence interfaces, while each criterion needs its own projection and standards. Current needs do not justify a generic plugin system; I prefer direct, inspectable calls.

The loop around a change

Form a testable hypothesis → freeze comparison conditions → record complete attempts → grade separate dimensions → inspect changes and failures → retain, revise, or gather more evidence.

This attempt did not establish that changing the prompt improves repair. It did reveal design choices worth testing. Next, I want each change to correspond to new evidence. The code and records remain available for inspection, corrections, and further exploration with other tasks and models.
